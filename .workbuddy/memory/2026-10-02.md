1. **qlib 返回的 MultiIndex 层序是 `['instrument','datetime']`（个股在前！）**。`groupby(level=0)` 会变成按个股分组 → n_days=4357（远超 1599 个交易日），RankIC 算成 0.0101（错误值）。必须用 `find_levels()` 按 index 名/datetime 唯一值数定位日期层，修正后 n_days=1596、RankIC=0.0281 才对。

## 2026-10-02 深夜｜复验器排查：定位 3 个真 bug + 一个口径级错误（重要）
起因：用户反馈"刚才好像出现了一些问题"，要求定位/根因/修复。现场核查（无残留进程、ollama PID 52284 存活、git 干净）后逐一排查，结论如下。

### 1) 429 too many requests —— 外部限流，非代码问题
出现在连续触发多个重后台任务时。非仓库逻辑缺陷，后续应串行化 + 退避重试。

### 2) `oos_validate.py` gross/net 口径 bug（真数据错误，已修）
- 位置：`oos_validate.py` 主循环 `"gross_ann": st["annualized"]`。
- 根因：`perf_stats()` 吃的是 `net_ret`（已扣费序列），`st["annualized"]` 本身净年化；同一个值被同时赋给 `gross_ann` 和 `net_ann` → **毛/净两列恒等**，扣费前后"毛收益"对比彻底失真（19:17 与 20:05 两份 CSV 数字完全一样）。
- 修法：`gross` 单独用零成本档（bps=0）跑一次再取年化；新增 `net_minus_gross` 与「成本吃掉比例 1-net/gross」输出。
- 注：先前的净收益数字（20bps 时 test 段 0.0002）是**对的**，错的只是被误标成 gross 的那一列。

### 3) `TS_ZSCORE` / `TS_PCTCHANGE` 无对应 qlib 算子 → 本轮新最优因子根本没被复验
- qlib 只有 52 个驼峰算子，没有 Zscore/Pctchange。这俩在映射表里缺失，导致本轮 top2 新最优（Variance-Volume Divergence、Tail-Exposure Momentum）全被 `is_qlib_compatible` 跳过，复验退化成只看 F0/F1，文件名写 top5 实际只出 2 行。
- 修法：新增 `_expand_ts_funcs()` 做表达式重写（非改名）：
  - `TS_ZSCORE(x,N)` → `(x - Mean(x,N)) / (Std(x,N) + 1e-8)`
  - `TS_PCTCHANGE(x,N)` → `x / Ref(x,N) - 1`
- 坑：正则实参要能吃**一层嵌套括号**并多轮迭代，否则 `TS_ZSCORE(ABS($return),10)` 漏网 → 最后被通用归一变成 qlib 未注册的 `Zscore` → 跳过。漏网时不会算错，但白瞎一条因子。

### 4)【最严重】复验前瞻收益口径与平台不一致，会系统性虚高 ~60%（已修）
- 复验器原用 `Ref($close,-h)/$close-1`（等价于让 t 日信号直接赚 t→t+1 的钱）。
- 平台真实口径见 `configs/backtest.yaml:39`：`dataset.label = "Ref($close, -2) / Ref($close, -1) - 1"`，语义是「t 日收盘出信号、t+1 才成交」。
- 实测（单因子 F0）：`Ref($close,-1)/$close-1` → spearman IC **0.0281**；`Ref($close,-2)/Ref($close,-1)-1` → **0.0174**。用错口径会虚高 60%。
- 已把 `fwd_expr` 改成 `Ref($close, -{h+1}) / Ref($close, -{h}) - 1` 与平台对齐。
- 另外旁证：qlib 官方 `contrib/report/analysis_position/score_ic.py` 的 docstring 用的就是 `Ref($close, -2)/Ref($close, -1)-1`。

### 5) 仍未解：平台 RankIC 0.0637 无法独立复现
