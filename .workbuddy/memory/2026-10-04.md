## 【决定性发现】唯一真实的 Alpha 是「低风险异象」，而且被 LGB 的符号掩盖了

15 条 Top 因子独立 RankIC（平台自报清一色 0.0596~0.0637）：

| 因子 | 平台 | 独立复算 | train/valid/test |
|---|---|---|---|
| F2 Vol_Spike 动量+放量 | 0.0637 | **−0.0321** | −0.029 / −0.040 / −0.035 |
| F11 Tail_Risk 振幅×动量 | 0.0600 | **−0.0268** | −0.023 / −0.040 / −0.029 |
| F12 Quiet_Fear 低波+负偏 | 0.0596 | **+0.0238** | +0.021 / +0.033 / +0.024 |
| F4 Vol_Corr 量价相关 | 0.0635 | −0.0229 | 三段同号负 |
| F9 Tail_Risk 振幅×动量符号 | 0.0600 | −0.0222 | 三段同号负 |
| F14 Asym_Quiet 偏度×波动比 | 0.0596 | −0.0207 | 三段同号负 |
| F6/F7/F8（Count 类） | 0.0605 | +0.0038 / −0.0014 / −0.0014 | 几乎为零 |
| 其余（F0/F1/F3/F5/F7/F10/F13） | 0.0596~0.0637 | −0.0097 ~ +0.0174 | 噪声 |

**两条结论**：
1. **平台 0.06 没有任何单因子能复现** → 全靠 LightGBM 多因子合成，单因子输入是噪声。
2. **波动/振幅/尾部风险族在 A 股是稳定负向的** —— 6 条里 5 条 train/valid/test **三段同号**，
   幅度 −0.02~−0.032。这是**低风险异象（low-risk anomaly）+ 反转效应**，批次里唯一的真信号。
   唯一的例外 F12 靠内置 `-1 *` 把符号掰正了才变成 +0.024 → 说明平台写了负号但没被单独验证，
   LGB 把它当普通输入权重吸收，方向信息丢失。
   → **取负号后 RankIC 就是 +0.032 / +0.027 / +0.023，是目前最强的单因子族。**

方法论教训：**只看 RankIC 绝对值会漏掉整个信号族**。必须同时看**符号与分段一致性**，
否则一个"负 Alpha"会被当成噪声丢掉，或者反过来被 LGB 学成正贡献。

### 【重要 bug】跑非默认数据集时，`.env` 的 QLIB_DATA_DIR 会抢走你的配置

现象：命令行明明 `QLIB_DATA_DIR=D:/qqmt/qlib_data/cn_5m_full`，
qlib 初始化却是 `data_path={'__DEFAULT_FREQ': WindowsPath('C:/Users/lenovo/.qlib/qlib_data/cn_real_full')}`。

根因（两处叠加）：
1. `runner.py:_init_qlib` 优先级是 `QLIB_DATA_DIR env > QLIB_PROVIDER_URI > self.config['data']['provider_uri']`，
   **环境变量压过配置**；而 `.env` 里写死了 `QLIB_DATA_DIR=C:/Users/lenovo/.qlib/qlib_data/cn_real_full`
   （日频默认），env loader 会**强制覆盖命令行传入的同名变量**。→ 設命令行根本不管用。
2. `runner.py` 只认 **`data:` 段**的 provider_uri，而我按 `conf_baseline_5min.yaml` 的写法放在
   **`qlib_init:` 段** → 即使环境变量不存在也会 KeyError / 拿错。

修复（commit `2fd6f3b`，最小侵入，不动 .env 所以不影响日频任务）：
```python
cfg_data = self.config.get('data') or {}
if cfg_data.get('force_provider_uri') and cfg_data.get('provider_uri'):
    provider_uri = cfg_data['provider_uri']          # 数据集自己说了算
else:
    provider_uri = (os.environ.get('QLIB_DATA_DIR')
                    or os.environ.get('QLIB_PROVIDER_URI')
                    or cfg_data.get('provider_uri')
                    or (self.config.get('qlib_init') or {}).get('provider_uri'))  # 补兜底
```
5min conf 里相应加：
```yaml
data:
    provider_uri: "D:/qqmt/qlib_data/cn_5m_full"
    freq: 5min
    force_provider_uri: true
```
验证：显式 `os.environ['QLIB_DATA_DIR']=...cn_real_full`（模拟 .env 抢占）后仍能落到 cn_5m_full。
**以后要在 QuantaAlpha 里跑任何非默认数据集（5min / 别的 frequency / 别的池），必须加这个开关。**

→ **`mine` 命令根本不读 `experiment_*.yaml` 里的 `backtest.qlib.config_name`**，只看环境变量
`QUANTAALPHA_BACKTEST_CONF`，取不到就回落到**日频 `conf_baseline.yaml`**。
（BacktestRunner 那条路是 `quantaalpha backtest` 用的，与挖掘无关。）
所以「在日频 experiment 配置里写 config_name」是无效的，必须这样启动：
```
CONDA_DEFAULT_ENV=quantaalpha QUANTAALPHA_BACKTEST_CONF=conf_5min_nextday.yaml \
  PYTHONPATH="D:/qqmt/QuantaAlpha/tools" PYTHONUTF8=1 RD_CPU_FRACTION=0.8 \
  -m quantaalpha.cli mine --direction "$(cat data/results/direction_5m.txt)" \
  --config_path configs/experiment_5min.yaml
```
模板文件必须放在 `quantaalpha/factors/factor_template/<config_name>`。
确认生效的标志：日志出现 `Execute factor backtest (Use Local): conf_5min_nextday.yaml`，
且 qlib 的 `data_path` 是 cn_5m_full（**日频 cn_real_full 一行都不该有**）。

### 【第 3 个坑】PortAnaRecord（组合回测）要 resample 到 **1min**，5min 数据集必崩

现象：模型训练成功、指标都出来了，**但**整条 workflow 结果回传为空，
pipeline 侧表现为 `Combined Results are an empty DataFrame` + `RankIC=None`，
feedback 的 LLM 只会看到"因子失败了"，白跑一轮。

真因（日志里在指标之后紧接着）：
```
qlib.workflow utils.py:41 - An exception has been raised
[ValueError: can't find a freq from Freq(5min) that can resample to 1min!]
  qlib/cli/run.py:157 run() -> ... backtest / strategy ...
```
→ qlib 的组合回测在做**成交模拟**时需要更细的 1min 频率，数据集只有 5min 就抛错。
（用户已明确"1 分钟先不补"，所以不能靠补数据解决。）

修法：5min conf 的 `record:` **只挂 SignalRecord + SigAnaRecord，不挂 PortAnaRecord**。
理由两条：① 它必崩且崩在指标算完之后，会连累结果回传；
② 就算不崩净值也不可信 —— `TopkDropoutStrategy` 不理解 A 股 T+1，会做出"当日买当日卖"。
本轮只用 **IC / RankIC** 评判，`port_analysis_config` 保留但不挂载。

### 分钟级第一次跑通的实测指标（LGB 合成口径）
```
IC 0.0526 / ICIR 0.543 / Rank IC 0.0413 / Rank ICIR 0.289
```
参考对比：日频那一轮平台报的 LGB 合成 RankIC 是 0.0596~0.0637，**单因子独立复算无一超过 ±0.03**。
分钟级这条 Rank IC 0.0413 同样是 LGB 合成口径，**单因子质量还必须用复验器独立复算才算数**
（现有 `tools/oos_validate.py` 只支持日频，改造支持 5min 是下一步必做的事）。
另外 ICIR 仅 0.289，且样本按 5min bar 重叠 → 显著性要打折看。

### 【第 4 个坑，最隐蔽】IC/RankIC 算出来了，但 pipeline 拿到的是 RankIC=None

去掉 PortAnaRecord 之后依然 `RankIC=None`。根因链路：

```
rdagent QlibFBWorkspace.execute()
  -> qrun <conf>
  -> python read_exp_res.py          # 生成 qlib_res.csv + ret.pkl
  -> if not (workspace/"ret.pkl").exists():
         logger.error("No result file found."); return None, log   # ← 直接返回 None
```

而 rdagent 原版 `read_exp_res.py` 最后一行是**无条件**的：
```python
ret_data_frame = latest_recorder.load_object("portfolio_analysis/report_normal_1day.pkl")
ret_data_frame.to_pickle("ret.pkl")
```
没挂 PortAnaRecord 就没有这个 object → 抛异常 → **ret.pkl 不生成** → execute 返回 None
→ `controller._extract_metrics(None)` 全 None → `trajectory.get_primary_metric()` = None。
（所以"去掉 PortAnaRecord"和"必须生成 ret.pkl"是一对矛盾，只改 conf 解决不了。）

修法：在 `quantaalpha/factors/factor_template/read_exp_res.py` 放健壮版覆盖默认模板
（该文件会被 `QlibFBWorkspace.inject_code_from_folder` 注入到每个 workspace，commit `b6cf7e8`）：
metrics 照常落 `qlib_res.csv`，`ret.pkl` 拿不到就写占位（它只用于画净值图，不影响 IC 类指标）。
**判据**：`Task done: trajectory_id=..., RankIC=0.04xx` 而不是 None。

### LLM 对分钟级方向的采纳情况情况（已核验）
第一条 `-RANK(ABS(DELTA($close, 47)) / (TS_SUM(ABS($return), 48) + 1e-8))`
—— 窗口 **47/48**（= 1 个交易日）、**单个** `-RANK(...)` 取负，正是方向串里写的路径效率因子。
（因子名字里的 `5D` 后缀是日频惯性，但表达式本身是对的，别被名字骗。）

## 【本轮结果无效】5m R1 跑完 13 条轨迹，RankIC 全是同一个数

`data/results/mining_5m_r1_postmortem.md` 是完整复盘。要点：

- 13 条轨迹 `RankIC` **全部 = 0.0413075135943158**（16 位小数都相同），
  但它们的**因子表达式确实各不相同** → 结果无效，不能采信。
- 证据：`Render the template`(qrun) 13 次，但 `factor_backtest took` 只有 **2 次**、
  `best score` **0 次**；workspace 里的 `mlruns/0/` **只有 meta.yaml、没有任何 recorder**；
  项目根 `mlruns/` 最后修改是 **10-02**（早于本次）→ 本次 qrun 没在 workspace 建 recorder，
  `read_exp_res.py` 的 `R.list_recorders()` 从别处读到了**陈旧 recorder**，每次返回同一份旧指标。
- **真正的 workspace 在 `git_ignore_folder/RD-Agent_workspace/<hash>/`**，
  不是 `data/results/workspace/`（后者只有 factor.py/result.h5，没有 mlruns）—— 排查时别找错。

### 教训：给"结果读取"加兜底必须同时加新鲜度校验
我为绕过 PortAnaRecord 写的占位 `ret.pkl` 兜底，解决了"返回 None"，却**掩盖了失败**：
rdagent 的 `execute()` 只检查 `ret.pkl` 是否存在，占位一写它就认为成功，
于是陈旧 IC/RankIC 被当成新结果写进轨迹池和 feedback。
**把旧值当新值返回，比直接报错更危险。**
修法：tracking URI 钉死到 workspace 内 mlruns + 只接受 start_time 晚于本次 qrun 的 recorder，
否则不写 qlib_res.csv，让 execute() 诚实返回 None。

## 【重大更正】5min 挖掘 R1 指标恒定的真因（前一条"陈旧 recorder"结论作废）

### 决定性证据
- 各 workspace 因子列名**各不相同** → 不是"同一份因子数据"
- 各 recorder uuid **各不相同**，是真生成的（位置：`mlruns/<随机exp_id>/<uuid>/`，
  不是 `mlruns/0/`；`0` 是 read_exp_res.py 里 `qlib.init()` 新建的空 Default exp）
- **各 workspace 的 `pred.pkl` md5 完全相同** `4d587ba575` ← 模型输出没随输入变化
- 因子表 index = 1599 个**日期**（日频）；pred index = 1968 个 **5min 时间戳** × 499 只
- 全库 54 条结果里 37 个 RankIC 互不相同，**只有 0.04130751359431582 被 17 条共享**
  → 日频轮正常，坏的只有 5min 轮

### 真因 = 两个叠加 bug
1. **因子没进模型**：`conf_5min_nextday.yaml` 只写了单个 `QlibDataLoader`（4 个写死特征），
   漏了 `NestedDataLoader` 里的第二个 `StaticDataLoader`（读 `combined_factors_df.parquet`）。
   日频版 `conf_combined_factors.yaml` 有，我抄的时候丢了。
   → 17 次都在评估同一个 4 特征基线，**0.0413 是基线数，不是任何因子的成绩**。
2. **因子算在日频上**：factor.py 第一行写死 `pd.read_hdf('./daily_pv.h5')`，
   这份 h5 是日频的 → 因子 index 是日期，与 5min label join 不上。
   **因子频率只由 daily_pv.h5 决定，与回测侧 conf 的 provider_uri/freq 是两条独立的线。**
3. 附带误判：LLM 实际用的是 `TS_MEAN($close,20)` 这类**日频窗口**，不是 48/47；
   它读到的是日频 README，没被有效告知数据频率。

### 已修（commit b974cfe）
1. conf → NestedDataLoader + StaticDataLoader
2. `tools/gen_pv_5min.py` 生成 5min 价量（liquid500，374 万行，含 `$vwap`，

4. `read_exp_res.py`：recorder `start_time` 必须晚于 `combined_factors_df.parquet` 的 mtime
   （比"钉死 tracking URI"可靠，因为 workspace 按内容 hash 复用、天然残留旧 recorder）；
   pred.pkl 必须非空；不过则不写 qlib_res.csv，诚实返回 None
