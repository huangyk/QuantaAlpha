# 数据架构：miniqmt 收紧后的应对方案

日期：2026-10-08　｜　结论：**研究/回测所需的历史数据已经全部在本地，不依赖任何券商接口。**

---

## 一、先分清两件事

你担心的「以后只能在 QMT 或 Ptrace 中使用」，其实要拆成两个完全不同的问题：

| 问题 | 是否受影响 | 说明 |
|---|---|---|
| **① 交易（实盘下单）** | 是 → 只能用 QMT 或 Ptrade | 但这是必然的，也不影响研究；战法代码 `pool_hold.py` 与下单接口解耦，换平台只需改适配层 |
| **② 历史行情数据（研究/回测）** | **否 → 完全不受影响** | 历史数据已经在本地 TimescaleDB 里，**不需要再从任何券商接口拉** |
| **③ 增量更新（每天新增的行情）** | 是 → 需要 QMT 或 Ptrace 之一 | 二选一即可，二者都是券商正式平台，比 miniqmt 稳定得多 |

**核心结论：即使 miniqmt 完全停用，QuantaAlpha 的历史研究能力不受任何影响。**

### [坑] volume 单位是「手」

判据（实测）：`amount / (close * volume)` ≈ 100（**日线与 5min 都成立，2011/2016/2020/2026 稳定在 99~100**）

**成交额 = close x volume x 100**；能用 `amount` 字段时**优先用 amount**（bars_1d / bars_5m 都有真实成交额）。

> 这个坑在 2026-10-08 之前一直存在，导致流动性/参与率/冲击成本结论被高估：
> 成交额低估 100 倍 -> participation 高估 100 倍 -> 冲击成本高估 10 倍。
> 详见 MEMORY.md「成交量单位陷阱」。

## 三、目标架构

```
┌─────────────────────────────────────────────────────────┐
│  数据底座（本地，不依赖券商）                             │
│  TimescaleDB bars_1d  2011-2026 全 A 5364 只              │
│  含 amount / turnover_rate / float_shares / total_shares│
└───────────────┬─────────────────────────────────────────┘
                │  ETL（需要时重建，不重建也能用）
                ▼
┌─────────────────────────────────────────────────────────┐
│  Qlib 数据集（研究/回测）                                 │
│  cn_real_full  ← 由 DB 重建，可扩到 2011 至今             │
│  cn_5m_full    ← 由 DB 的 bars_5m 重建                   │
└───────────────┬─────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────┐
│  QuantaAlpha 策略层（离线，不联网）                        │
│  pool_hold.py 等 —— 与下单接口解耦                        │
└───────────────┬─────────────────────────────────────────┘
                │  只在实盘环节需要券商
                ▼
┌─────────────────────────────────────────────────────────┐
│  实盘执行：QMT 或 Ptrace（二选一）                        │
│  职责：① 每日增量拉行情  ② 下单  ③ 持仓同步              │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：
1. **研究层完全离线** —— 跑任何回测都不需要连券商、不需要联网。
2. **增量更新是唯一依赖券商的环节** —— 且只是一天的数据，量极小，
   即使 QMT/Ptrade 有任何限制，也不影响已有 16 年历史。
3. **策略代码与下单接口解耦** —— `pool_hold.py` 只负责「算权重、算股数、给执行时点建议」，
   下单由平台适配层完成，换平台不改策略逻辑。

## 四、需要做的三件事（按优先级）

### ① 代码格式映射（必须做，一次性）
两个库的标的口径不同：

```
TimescaleDB:  600000.SH   000001.SZ     （后缀）
Qlib:         SH600000   SZ000001     （前缀）
```

需要一个映射函数（`SH600000 ↔ 600000.SH`），
在 DB→qlib 的 ETL 里统一处理。**注意库里同时含指数**
（如 `000001.SH` 实际是上证指数，close 3842.194），需要用 `asset_type` 过滤。

### ② DB → Qlib ETL（建议做）
有了它就能：
- 把回测区间从 2020 扩到 **2011**（多 9 年，对验证风格稳定性极有价值）
- 顺便把 `amount`、`float_shares` 做成因子（换手率、市值中性化）
- qlib 数据集丢失后可随时重建，不再依赖某次抓取

### ③ 增量更新脚本（实盘前必须做）
每天收盘后从 QMT 或 Ptrace 拉当日行情 → 写入 `bars_1d` → （可选）重建 qlib bin。

## 五、风险与兜底

| 风险 | 兜底 |
|---|---|
| 两个平台都限制历史下载 | 已有的 16 年历史足够；增量只需下当天数据 |
| 平台接口变更 | 增量脚本是唯一受影响的部分，且是薄层；研究/回测不受影响 |
| 本地 DB 损坏 | 建议对 `bars_1d` 做定期备份（`pg_dump`），它是整个体系的地基 |
| 分钟级数据无法回补 | 已确认 QMT 侧 5min 只能到 2026-01、1min 到 2025-04；日内研究需在现有窗口内做 |
